# Host Monitoring Completion

Before this change, enabling `HostMonitoringEnabled` (`pkg/config/config.go`) got you a virtual "host" pseudo-container (`pkg/containerwatcher/v2/container_watcher_collection.go`) with two working pipelines — rule/alert evaluation and network-stream mapping — and three broken ones: application-profile generation silently stalled, SBOM generation was an explicit no-op, and malware detection was an explicit no-op. This document describes how all three were unblocked, and the one genuine bug found along the way.

## Why profile and SBOM needed different fixes

Profile generation and malware detection share a single root cause: both wait on `k8sObjectCache.GetSharedContainerData`, which returns `nil` for host because nothing ever populates it — there is no real Kubernetes pod backing the host pseudo-container. SBOM generation does not share that root cause at all: the container SBOM path is driven entirely by image/mount data (`ContainerImageName`, `getMountedVolumes`, `imageStatus`) that a host simply doesn't have, regardless of shared-container-data. Treating all three as "one fix" (an earlier draft of this work did) doesn't survive contact with the code — SBOM needed its own, wholly separate scan branch.

## The shared host-identity builder (`pkg/hostidentity`)

`pkg/hostidentity` resolves a stable per-node identity and builds the synthetic, K8s-shaped values that profile and malware detection need:

| Function | Purpose |
|---|---|
| `ResolveHostID(cfg *config.Config) (string, error)` | Primary source is `cfg.NodeName` (populated from the `NODE_NAME` downward-API env var — stable across restarts). Falls back to `$HOST_ROOT/etc/machine-id` only if `NodeName` is empty. Returns an error rather than silently returning `""` — a caller getting an empty identity string is worse than a caller handling an error. |
| `BuildHostWlid(hostID)` | `wlid://cluster-unknown/namespace-host/host-<hostID>` |
| `BuildHostInstanceID(hostID)` | A real `instanceidhandler.IInstanceID` (not a string) with `InstanceType`/`TemplateHash` set explicitly, since both surface via `GetLabels()`. |
| `BuildHostWatchedContainerData(hostID)` | A `WatchedContainerData` with every field explicit — `ContainerID="host"`, `Namespace="host"`, `ContainerType=containers` (there is no dedicated `Host` enum value), `PreRunningContainer=false`, `UserDefinedProfile=""` (this is a **string** field, not `bool`), and a single-entry `ContainerInfos` map (see "the ContainerInfos crash" below). |

This package lives outside `pkg/utils` deliberately: `pkg/utils` is imported by `pkg/objectcache`, which `WatchedContainerData` itself lives in, so placing the builder in `pkg/utils` would create an import cycle.

`pkg/hostsensormanager.HostFSPrefix()` was exported (it was previously the unexported `hostFSPrefix`, sourced from the `HOST_ROOT` env var) so both this package and the SBOM host branch can read the same host-filesystem-mount convention without re-deriving it.

## Single injection point

`pkg/containerwatcher/v2/containercallback.go` used to skip shared-data setup for host entirely. It now branches explicitly: `utils.IsHostContainer(...)` routes through the `hostidentity` builder and `k8sObjectCache.SetSharedContainerData("host", ...)`; everything else is unchanged. This is deliberately a **replacement**, not a deletion of the skip — falling through to the real-container path would call `k8sClient.GetWorkload("", "")` for a workload that will never exist, retried on an unbounded exponential backoff, leaking a goroutine per node forever.

## Consumer audit

Once `GetSharedContainerData("host")` stopped returning `nil`, every consumer that assumed non-nil implies "this is backed by a real Kubernetes object" needed a look — a well-formed-but-fake K8s lookup result is worse in a security agent than a loud, obvious skip. Sites audited:

| Site | Disposition |
|---|---|
| `pkg/rulemanager/profilehelper/profilehelper.go` (`GetPodSpec`) | **Guarded.** Host returns an empty `PodSpec` instead of attempting a live lookup that would always miss. |
| `pkg/rulemanager/ruleadapters/creator.go` (`setRuntimeAlertK8sDetails`, PodUID/WorkloadUID) | **Guarded.** This is a separate function from the presence-based check in `setProfileMetadata` — it was not already covered. |
| `pkg/containerprofilemanager/v1/lifecycle.go` (shared-data read) | **Already safe** — pure cache read, no K8s-specific sub-call. What changed is that it now *succeeds* instead of spinning to the wait deadline. |
| `pkg/rulemanager/containercallbacks.go` | **Already safe** — `rule_manager.go`'s pre-existing `IsHostContainer` bypass means this is never reached for host. |
| `pkg/networkstream/v1/network_stream.go` | **Unchanged, verified by regression test** — its existing host handling doesn't rely on shared data being `nil`. |
| `pkg/objectcache/containerprofilecache/containerprofilecache.go` | **The site that was stalling.** Now proceeds and reaches storage; covered by an end-to-end test. |
| `pkg/sbommanager/v1/sbom_manager.go` | **Unreachable for host** — host now short-circuits into its own branch (see below) before this point is ever reached. |

The dead scaffolding fields `hostProfile`/`hostProfileMu`/`hostID` in `containerprofile_manager.go` were deleted — nothing in the repo referenced them.

**No change to the alert payload.** `creator.go`'s `setProfileMetadata` used to check `if state != nil` before attaching `ProfileMetadata` — but `GetContainerProfileState` never actually returns `nil` (it synthesizes an error state when profile data is absent), so that check was dead code, and every alert got a `ProfileMetadata{Type, ProfileDependency, Error}` regardless of whether a profile actually existed. An earlier draft of this fix replaced that dead check with `state.Error == nil`, which turned out to be a real (if narrow) regression: it withheld `ProfileMetadata` entirely — including the `Error` field — whenever a profile was absent, for host and real containers alike. The final version instead always attaches `ProfileMetadata` (as the code always effectively did, since the old check never actually filtered anything) and continues to surface `state.Error` via the `Error` field when present — restoring the original behavior for real containers while extending it correctly to host.

## The ContainerInfos crash

A test that drove real exec/open/syscall/capability events through the host profile pipeline and asserted the resulting CR actually contained that data (not just an empty shell) caught a real bug: `hostidentity`'s synthetic `WatchedContainerData` didn't set `ContainerInfos`, and `monitoring.go`'s `saveContainerProfile` unconditionally indexes `ContainerInfos[ContainerType][ContainerIndex]` when building the CR. Host's first successful save would have panicked. Fixed by giving the synthetic data a single-entry `ContainerInfos` map.

## Profile finalization

`calculateSniffingTime`/`handleContainerMaxTime` (`pkg/containerprofilemanager/v1/lifecycle.go`) apply a fixed `MaxSniffingTime` timer to every container and delete the entry when it fires — correct for a bounded container lifetime, wrong for an always-on host. `EnableRuntimeDetection`/`EnablePartialProfileGeneration` were investigated as a possible mitigation and confirmed **not** to help: they only gate pre-running-container admission, and are never read by the finalization timer. The fix is a direct bypass: the timer is simply never armed for the host pseudo-container (mirroring the existing `IsHostContainer`-bypass convention used elsewhere, e.g. `rule_manager.go`), leaving real-container finalization completely unchanged.

**Consequence, and the follow-up fix.** `ContainerReachedMaxTime` (`monitoring.go`) is the only path a real container's profile uses to reach `WatchedContainerStatusCompleted`, and it is never sent for host (the timer that would raise it is never armed). Initially this meant the host profile stayed non-terminal forever, which `containerprofilecache.go`'s `tryPopulateEntry` never caches (it only caches `Completed`/`TooLarge`) -- so the host profile would never be installed for `GetProjectedContainerProfile`, and `creator.go`'s `FailOnProfile: state.Status == helpersv1.Completed` could never be `true` on a host alert regardless of how much the profile had converged. This was fixed separately: `monitorContainer`'s regular per-tick status update now sets `Completed` (instead of `Ready`) once the same duration a real container's initial-learning timer would use has elapsed (`watchedContainer.LearningPeriod`, computed once in `addContainer` and reused here rather than recomputed, since `calculateSniffingTime` applies random jitter and a second call would silently drift from the value reported in labels) -- but, unlike `ContainerReachedMaxTime`, does not stop the loop, so host keeps collecting and saving fresh data indefinitely once consumable. `FailOnProfile` therefore behaves for host the same way it does for a real container once the profile's learning window elapses, not never.

## SBOM: a separate scan branch

`pkg/sbommanager/v1/host_sbom.go` is a standalone branch — it never touches `k8sObjectCache`/`SetSharedContainerData`, and never calls into the image/mount-driven `awaitAndSubmit` machinery the container path uses.

**Scan source.** `pkg/sbommanager/v1/syftutil/directory_source.go` adds a Syft directory-source construction (`directorysource.New`) pointed at `HostFSPrefix()`'s path, with an explicit `Exclude` list so the scan doesn't ingest every container image layer on the node:

```
./var/lib/containerd/**  ./var/lib/docker/**  ./var/lib/containers/**  ./var/lib/rancher/**
./run/containerd/**      ./run/docker/**      ./run/crio/**
./proc/**  ./sys/**  ./dev/**
```

Two non-obvious Syft API details, pinned by tests:
- Exclusion patterns must be **scan-root-relative**, starting with `./`, `*/`, or `**/` — an absolute pattern like `/var/lib/containerd/**` is rejected outright by `directorysource.GetDirectoryExclusionFunctions`.
- That same function **mutates the exclusion slice in place** (prefixing each entry with the root). The host scan clones the exclusion list before each use so a second scan doesn't get double-prefixed patterns.

**Cadence.** One scan at host registration, plus a periodic re-scan on `HostSBOMRescanInterval` (new config field, default 24h — containers have no periodic re-scan at all, only event-triggered reprocessing on a scanner-version bump, so this is genuinely new, host-only behavior). The host scan loop runs on its own goroutine, not the shared container-SBOM worker pool, so a full host-root walk can't head-of-line-block container SBOM generation.

**Interaction with the `TooLarge` state machine.** A `TooLarge` trip blocks only the current rescan attempt, not future ones. Unlike the container path -- which releases on a Syft tool-version bump or a change to the sidecar's scanner-memory-limit annotation -- host always scans in-process (it has no sidecar), so it's released by a change to `cfg.MaxSBOMSize` instead, recorded via the dedicated `HostMaxSBOMSizeAnnotation` (reusing the sidecar's `ScannerMemoryLimitAnnotation`/`scannerMemLimit` here would never release the block, since host's `scannerMemLimit` is always `0`). A permanent block would mean a node could never recover after a config change; an unconditional retry would burn a full root-filesystem walk every interval only to have the result dropped by storage's one-way-door write guard.

`Incomplete` status is ambiguous about whether a scan ever actually completed: it's set both when a good-or-oversized scan result is deliberately kept back from the one-way `TooLarge` door, and via an annotation-only patch (`markSBOMStatus`) after repeated scan *failures* — which can fire on an SBOM that never completed a scan at all. `prepareHostSbom` disambiguates using `ResourceSizeMetadataKey`, an annotation set exactly once a scan completes and never cleared by that annotation-only patch, rather than assuming either answer for every `Incomplete` SBOM.

**Naming and failure reporting.** The `SBOMSyft` CR is named/labeled from `hostidentity.ResolveHostID`, not image-derived fields. `reportFailure` (the kubevuln-facing scan-failure report, keyed by `ImageTag`/`ImageHash`/pod `WorkloadIdentifier`) is explicitly skipped for host via a documented no-op — none of those fields exist for a host scan.

**Scan timeout.** The Syft scan runs under a 16-minute `context.WithTimeout` (matching the container path's sidecar-scan bound) rather than the bare manager-lifetime context — a host-root walk hung on a slow mount is bounded, not indefinite. A timeout reports a distinct `"timeout"` metric outcome (alongside the existing `"success"`/`"error"`) and falls through the same failure handling as any other scan error, which unconditionally clears the in-flight `processing` marker — so a timed-out scan is recoverable on the next rescan tick, not a permanent stall.

## Vulnerability scanning stays external

node-agent never performs vulnerability scanning (CVE matching) for containers or the host — it only produces `SBOMSyft` CRs. `kubevuln` is a fully separate, externally-deployed component that consumes those CRs; it needed no changes here. No `SBOMSyftFiltered` or relevancy-filtering mechanism exists in this repo — `containerprofilecache`'s `projection_compile.go`/`reconciler.go` are unrelated rule-engine runtime-projection code (opens/execs/syscalls for the CEL rule engine), not SBOM filtering.

## Malware detection

`pkg/malwaremanager/v1/malware_manager.go` removed the `IsHostContainer` exclusion that previously dropped host before any tracking began, and added an explicit host bypass for the separate `IgnoreContainer` check immediately after it (host must not be dropped by ignore-list logic meant for real containers, e.g. namespace-based rules that could accidentally match an empty/host namespace). `reportFileExec`/`reportFileOpen` needed no changes — they key only on `containerID` against maps populated by the callback change, with no profile or K8s-specific branching.

## Fixes from post-merge review (real production gaps, not caught by the original test suite)

A GitHub Copilot review round found four issues the original tests missed entirely, because the shared host-container test fixture didn't match the real production object's shape:

- **Every ignore-list gate that runs ahead of a manager's own host handling needed an explicit host exemption.** `GetHostAsContainer` builds the host pseudo-container with an empty `K8s.Namespace`/`PodName`/`PodLabels` (it has no backing Kubernetes object). Any `cfg.IgnoreContainer(...)` check reached *before* a manager's own `IsHostContainer` bypass can therefore drop the host silently under realistic production configs — an `IncludeNamespaces` allow-list that doesn't list `""`, or `cfg.NamespaceName` itself being empty. `pkg/malwaremanager` and `pkg/sbommanager` already guarded correctly; `pkg/containerwatcher/v2/containercallback.go`, `pkg/containerprofilemanager/v1/lifecycle.go`, and `pkg/rulemanager/containercallbacks.go` did not — all three now check `utils.IsHostContainer` before `IgnoreContainer`. This means the rule/alert engine's host support (the one piece this whole feature originally assumed already worked) could itself have been silently broken under an `IncludeNamespaces` config.
- **The real host container's empty `K8s.Namespace`/`PodName` reached `saveContainerProfile`, which uses `container.K8s.Namespace` directly for the CR's own `Namespace` field.** The shared test fixture pre-populated those fields (`Namespace: "host"`), masking that the real object never gets them — the first host profile save would have failed to create against an empty namespace. Fixed with `hostContainerWithIdentity`, which copies the synthetic identity from `sharedData` into a local copy of the container before it's used, without mutating the object shared with every other subscriber of the add-container event. The shared test fixture (`newHostPseudoContainer`) was corrected to match `GetHostAsContainer`'s real (empty) shape, turning the existing content-population test into a genuine regression test for this.
- **`hostTooLargeReleased` checked the wrong size limit.** It recorded and compared `ScannerMemoryLimitAnnotation`/`scannerMemLimit` — the sidecar scanner's memory limit, which never applies to host (host always scans in-process with Syft). Since host's `scannerMemLimit` is always `0`, the size-based release condition could never fire, meaning increasing `cfg.MaxSBOMSize` could never unblock a stuck `TooLarge` host SBOM. Fixed with a dedicated `HostMaxSBOMSizeAnnotation`, compared against `cfg.MaxSBOMSize`.
- **`hostFSPrefix` and `hostRoot` could silently disagree.** `CreateSbomManager` resolved `hostRoot` locally (`HOST_ROOT` env, falling back to `/host` — matching the DaemonSet's actual mount) but set `hostFSPrefix` from `hostsensormanager.HostFSPrefix()` separately, whose own fallback is `/host_fs`. With no `HOST_ROOT` override, the two would disagree and the host scan would open a path the DaemonSet never mounts. Fixed by reusing `hostRoot` directly instead of a second, differently-defaulted resolution.

## Second review round: namespace, event-level filtering, name collisions, and duplicate registration

A further Copilot + CodeRabbit pass on the fixes above found five more issues, three of them severe:

- **The host `ContainerProfile` CR was being stored in a namespace that doesn't exist.** The earlier namespace/pod-name fix copied `sharedData.Namespace` ("host" — a synthetic identity label embedded in the Wlid/InstanceID, not a real Kubernetes namespace) into the container used for storage. `Storage.CreateContainerProfileDirect`/`GetContainerProfile` call `ContainerProfiles(namespace).Create`/`Get` directly against the API server, so the very first host profile create would fail with `NotFound` on any real cluster. Fixed by using node-agent's own deployment namespace (`cfg.NamespaceName`, guaranteed to exist) for the actual K8s storage calls in both `containerprofilemanager` (write) and `containerprofilecache` (read) — the "host" identity label itself is untouched, since it's just a string embedded in the Wlid, not a K8s API argument.
- **A second, separate `IgnoreContainer` gate on the runtime *event* stream** (`EventHandlerFactory.ProcessEvent`, `pkg/containerwatcher/v2/event_handler_factory.go`) was missed by the earlier container-lifecycle fix. Even with host correctly *registered*, every actual runtime event (exec/open/syscall/network) would still be silently dropped here under an `IncludeNamespaces` config — starving the profile/rule/malware handlers of all host behavior data while appearing to work. Now exempted the same way.
- **`hostSbomName`'s sanitizer was lossy enough to let two distinct hosts collide on the same storage key.** Character replacement plus truncation to 63 chars means e.g. `node.a` and `node-a` produce the same name, and two long hostnames sharing a 63-character prefix would too — silently letting one node overwrite another's SBOM. Fixed by appending an 8-character hash of the raw (pre-sanitize) hostID.
- **`hostidentity.ResolveHostID`'s machine-id fallback used a mismatched default.** It read via `hostsensormanager.HostFSPrefix()`, whose own fallback (`/host_fs`) differs from the `/host` default `pkg/sbommanager/v1` and the deployed chart actually use — so with `NodeName` empty and no `HOST_ROOT` override, host identity resolution would fail entirely even though the host filesystem is correctly mounted. Fixed by resolving `HOST_ROOT` independently in this package (mirroring `sbom_manager.go`'s identical inline logic, which this package cannot import without creating a cycle) rather than changing `hostsensormanager`'s own default, which is used by an established, separate host-sensor feature this work doesn't otherwise touch.
- **Container registration was an unconditional overwrite, not a get-or-insert.** `addContainerWithTimeout` replaced the container's map entry unconditionally; a replayed `AddContainer` notification (the container-watcher collection is known to do this, notably for the host pseudo-container) would orphan the earlier entry's monitor goroutine forever — `deleteContainer` only ever signals "the current" entry in the map, so the first monitor keeps running with no way to be stopped. Fixed with an atomic get-or-insert (`addContainerEntryIfAbsent`); a duplicate add is now a no-op.

One review claim was checked and found to be a false positive: that a `Learning`-SBOM rescan which turns oversized would send a metadata-only object (from `GetSBOMMeta`'s intentionally Spec-less read) and erase previously published content. In fact `wipSbom.Spec.Syft` is unconditionally overwritten with the fresh scan's content before the size check runs, so the `Incomplete` branch persists the new (if oversized) content, not an empty shell — verified with a dedicated test before deciding not to change this code.

## Third review round: host removal hang, terminal-state caching, and label collisions

A further Copilot pass found two more real gaps, plus a label-only extension of the earlier CR-name collision fix:

- **The host profile could never reach a *cacheable* terminal status.** `addContainer` deliberately skips arming the max-sniffing-time timer for host (so it's never finalized/deleted), but `containerprofilecache.go`'s `tryPopulateEntry` only ever caches a profile whose status is terminal (`Completed`/`TooLarge`) — so, without a separate path to `Completed`, the host profile would stay `Ready`/`Learning` forever and never become visible to `GetProjectedContainerProfile` or any profile-dependent CEL rule, no matter how much data it actually collected. Fixed in `monitorContainer` (`monitoring.go`): once the same duration a real container's initial-learning timer would use (`calculateSniffingTime`) has elapsed, the regular per-tick status update sets `Completed` instead of `Ready` — but, unlike the real `ContainerReachedMaxTime` signal, does not return from the loop, so host keeps collecting and saving fresh data indefinitely under a status callers can actually consume.
- **`deleteContainer`'s termination path risked a 30-second hang for host.** It calls `GetTerminationExitCode`, which retries for its full backoff window looking for a Kubernetes pod status that will never exist for a host pseudo-container, then marks the profile `Failed`. Host removal isn't expected in normal operation (by the time it could happen, the fix above will usually have already reached `Completed`, which the existing status guard already skips this block for) — but if it's ever reached regardless, it's now handled with an explicit `IsHostContainer` branch that sets `Completed` directly instead of waiting on a lookup that can never resolve.
- **Label collision, not just name collision.** The earlier hash-suffix fix protected the `SBOMSyft` CR's *name* from two different hostnames colliding after lossy sanitization, but `hostSbomLabels` still used the bare sanitized hostID for both label values — so two colliding hosts would still get identical labels even with distinct CR names. Fixed by extracting a shared `collisionResistantLabel` helper and using it for both the CR name and its labels.

A test-writing note from this round: two of the new regression tests for the fixes above (`TestHostContainerProfile_ReachesCompletedWithoutStopping`, `TestDeleteContainer_HostSkipsTerminationExitCodeLookup`) initially read `WatchedContainerData` fields from outside its owning `monitorContainer` goroutine without synchronization — `go test -race` caught this. `WatchedContainerData` has no internal lock by design (only its owning goroutine mutates it); the fix was to synchronize on the same happens-before edges production code already exposes for this purpose — the `entry.ready` channel closed once initial registration completes, and a new completion-notifier hook so tests can wait on a real "reached Completed" signal instead of polling. That hook, `cpm.notifyCompleted(...)` on the host tick's `Completed` transition, was itself a genuine gap: every *other* transition to `Completed`/`TooLarge` in `monitoring.go` already calls it (so `containerprofilecache`'s `CompletionNotifier` can promote a pending entry without waiting for its next reconciler tick) — the host tick path was the one place that didn't, so real consumers of that notification would never learn the host profile became consumable. Now guarded to fire exactly once (on the first tick past the learning deadline, not on every subsequent tick).

## Fourth review round: HOST_ROOT edge cases, a registration-retry gap, label/hash strength, and label reporting

A CodeRabbit + Copilot pass found four more real issues, all narrower in scope than earlier rounds:

- **An explicitly empty `HOST_ROOT` was treated as if it were set**, in both places that resolve it (`sbom_manager.go`'s `CreateSbomManager` and `hostidentity.go`'s `machineIDHostRoot`). `os.LookupEnv` reports an explicitly-empty env var as present, so `if !exists { hostRoot = "/host" }` (and the equivalent `if hostRoot, ok := ...; ok { return hostRoot }` in `hostidentity.go`) left `hostRoot`/`HOST_ROOT` as `""` rather than falling back to `/host`. An empty root fails the host Syft scan outright, and empty-string machine-id resolution reads the container's own `/etc/machine-id` instead of the host's. Fixed by treating an empty value the same as unset in both places.
- **A replayed `AddContainer` notification racing in while an earlier registration attempt for the same container was still pending, and that earlier attempt then failing, could leave the container silently untracked forever.** `addContainerEntryIfAbsent`'s "already tracked, skip" branch assumed the existing entry's `ready` channel closing meant success -- but `ready` closes on **both** success and failure (see the error/timeout branches in `addContainerWithTimeout`). A replay that observed the existing entry, waited (implicitly, by just returning) without checking survival, and never retried, would leave nothing tracking a container that a still-live watcher believes was added. Fixed by having a duplicate-add wait for the existing attempt's `ready` channel, then check whether its entry survived; if not, loop and retry the get-or-insert with its own entry instead of giving up. `TestContainerCallback_ReplayDuringFailingRegistrationRetries` is the regression test.
- **The host SBOM's collision-resistant hash suffix was only 8 hex characters (32 bits).** Two distinct host IDs producing the same sanitized/truncated base and colliding on that short a hash is unlikely but not negligible across a large fleet, and a collision would let one host's SBOM silently overwrite another's. Widened to the full 32 hex characters (128 bits) a SHA-256 digest provides; `collisionResistantLabel`'s `maxBaseLen` computation already accounted for the suffix length dynamically, so this required no other logic change (only updating one test's expectation for a long hostname, which now truncates further to make room for the wider suffix).
- **Skipping the max-sniffing-time timer for host also skipped recording `LearningPeriod` on the shared data**, since both lived in the same `if !utils.IsHostContainer(container)` block. `objectcache.GetLabels` emits `LearningPeriod` for every container regardless of type, so host profiles would report a `0s` learning period despite genuinely converging on a schedule. Fixed by computing and recording `LearningPeriod` unconditionally, only gating the timer's `time.AfterFunc` itself on `!IsHostContainer`. `monitorContainer`'s own Completed-transition deadline for host was changed to reuse this same recorded `LearningPeriod` value instead of calling `calculateSniffingTime` a second time -- that function applies random jitter, so a second call would silently compute a different duration than the one just recorded, making the reported label drift from the deadline actually used. `TestAddContainer_HostRecordsLearningPeriodWithoutArmingTimer` is the regression test.

Fixing the `LearningPeriod` race above (a test reading it concurrently with `addContainer`'s write) also surfaced that the write itself was not synchronized with `entry.mu` the way the adjacent `watchedContainerData`/`timer` field writes are -- a pre-existing gap for real containers too, just never previously exercised concurrently. Now written under the same lock.

One review claim in this round was already resolved by the time it was raised: Copilot's overview carried forward "host profiles never transition to a consumable terminal state," "preserve SBOM content on oversized rescans," "use an existing namespace for host profile storage," and "allow host events through namespace filtering" as still-open findings from its own prior review round, but all four were already fixed in this repository by the time this round's comments were posted (the completion-notifier fix, the refuted SBOM-content claim, the `cfg.NamespaceName` fix, and the `event_handler_factory.go` bypass, respectively, are all documented in earlier sections above) -- verified directly against current code before deciding not to change anything for them.

A documentation-only correction: the "Profile finalization" section above previously stated `FailOnProfile` is "permanently `false`" for host, which was accurate when written but became stale once the Completed-transition fix (documented in the third review round above) landed later in the same PR; it now describes the current, corrected behavior. Similarly, the `TooLarge`-release paragraph in the SBOM section now names `cfg.MaxSBOMSize` (the value host actually compares against) instead of implying the sidecar's scanner-memory-limit applies to host.

Also fixed: `TestResolveHostID_RetriesAfterFailure` (`pkg/containerwatcher/v2/containercallback_host_test.go`) forced its failure case via `hostsensormanager.SetHostFSPrefixForTest`, but `hostidentity.ResolveHostID`'s machine-id fallback reads `HOST_ROOT` directly and no longer goes through `hostsensormanager` at all -- so the test's forced failure depended on the sandbox it runs in not having a real `/host/etc/machine-id`, rather than on anything the test itself controlled. Fixed by also setting `HOST_ROOT` to the test's own empty temp directory.

## What is still out of scope

- Manual/live-cluster verification (`kubectl get sbomsyft`/`containerprofile` against a real host, observing live malware/alert events) was not performed — no live cluster is available in the environment this work was done in. The automated tests described above substitute for it: end-to-end profile-content population, real-Syft-scan exclusion fixtures, and Wlid-enrichment assertions on real malware events.
- Noise reduction / allowlisting for host-level malware and profile alerting (legitimate system daemons look different from container workloads) is a follow-up, not addressed here.
